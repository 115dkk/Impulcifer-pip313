## Design (fixed)
- **Install kinds** (`crates/impulcifer-service/src/update/install_kind.rs`): `velopack` (Windows, `Update.exe` in the parent of the executable's directory, exactly the 2.x probe), `tauri` (macOS: the executable lives inside a `.app` bundle `Contents/MacOS`; Linux: the `APPIMAGE` environment variable is set), `dev` otherwise. No `pip` kind: the PyPI wheel has no GUI and the CLI does not update. `bootstrap` reports the detected kind instead of the hardcoded `dev`; a `ServiceOptions`-style constructor argument (or an environment override `IMPULCIFER_INSTALL_KIND` used only by tests) lets tests force a kind.
- **`check_for_updates`** (`update/check.rs`): blocking HTTP GET of `https://api.github.com/repos/115dkk/Impulcifer-pip313/releases/latest` with a 10 s timeout through `ureq` (`default-features = false`, `rustls` TLS, no OpenSSL; add it to the service `Cargo.toml`), `User-Agent: Impulcifer/<version>`. Same version normalisation and comparison as 2.x, same asset selection rules per platform (Windows Setup exe, macOS dmg, Linux AppImage preferred; `None` when nothing matches), same response fields: `update_available` (newer and a download URL), `current_version`, `latest_version`, `download_url`, `release_notes` (only when an update is available), `release_url`. Failures: `UPDATE_CHECK_FAILED`, retryable. The endpoint base URL is a field so tests can point it at a local `std::net::TcpListener` mock (no network in CI).
- **`start_update`** (`update/mod.rs`): validation as 2.x (`latest_version` required, `download_url` optional string), job kind `update`, not cancellable, progress events `{"progress": 0..1, "message": <i18n key or preformatted text>}` with the same keys 2.x emits (`update_downloading`, `update_downloaded`, and the `"Downloading: NN%"` texts; read the executors), result fields exactly `status_key`, `status_default`, `title_key`, `title_default`, `message_key`, `message_default`, `progress`, `requires_restart`. The executor is chosen by install kind:
  - `velopack` (Windows only, `cfg(windows)`): the `velopack` Rust SDK. `UpdateManager` with an `HttpSource` on the same feed the 2.x packages use (read `updater/velopack.py::_fetch_release_manifest` and `_detect_channel` for the URL and channel names, keep them identical so 2.x and 3.x installs read one feed), `check_for_updates` then `download_updates` with progress mapped to the job, and stage `apply_updates_and_restart` for `apply_pending_update`. The SDK's `VelopackApp::build().run()` must run first thing in `apps/impulcifer-app/src/main.rs` on Windows (it handles install/uninstall hooks and exits early when invoked by `Update.exe`); add it behind `cfg(windows)`.
  - `tauri` (macOS/Linux): the service cannot link Tauri, so extend `HostAdapter` with `fn download_update(&self, latest_version: &str, progress: &(dyn Fn(f64, &str) + Sync)) -> Result<(), String>` and `fn apply_staged_update(&self) -> Result<(), String>` (default implementations return `Err("not supported")`), implemented in the app with `tauri-plugin-updater` (endpoint: the `latest.json` asset of the GitHub release, public key in `tauri.conf.json` `plugins.updater.pubkey`; generate a key pair with `tauri signer generate` into `%TEMP%` for the report and put the **public** key in the config, never the private key; the CI secret name `TAURI_SIGNING_PRIVATE_KEY` is documented for the packaging packet). `download_update` runs `check` + `download` with progress and keeps the downloaded update in the host; `apply_staged_update` installs and relaunches.
  - `dev` and unmatched bundles: the legacy executor as 2.x: download `download_url` to the OS temp directory with progress, verify against `SHA256SUMS.txt` next to it when present, then `HostAdapter::open_path` on the file (or replace the running AppImage when `APPIMAGE` names it, exactly as `updater/legacy.py`).
- **`apply_pending_update`**: runs the staged action recorded by the last successful `start_update` (`INVALID_REQUEST` "No staged update to apply." when none), returns `{"restarting": true}`; `UPDATE_FAILED` retryable on error. For Velopack the SDK hands over to `Update.exe` and the process exits; for Tauri the plugin relaunches.
- Catalogue keys: everything the frontend displays comes from existing `update_*` keys or preformatted text, exactly as 2.x. No new i18n keys in `i18n/locales`; 3.x-only texts go to `settings.rs EXTRA_STRINGS` if unavoidable.
